## Requirements
### Requirement: Provider-agnostic LLM interface

The backend SHALL expose a single `LLMProvider` protocol that every chat-capable adapter implements. Callers SHALL depend on the protocol only, never on a concrete provider SDK.

#### Scenario: Caller uses the protocol, not the SDK

- **WHEN** a backend router or service needs to talk to the LLM
- **THEN** it imports `LLMProvider` from `app.services.llm` and obtains an instance via `get_llm()`
- **AND** no router or service imports `ollama`, `openai`, or `anthropic` directly

#### Scenario: Adding a fourth provider does not touch callers

- **WHEN** a future contributor adds a `MistralProvider` implementing `LLMProvider`
- **THEN** no existing caller needs modification
- **AND** the change is limited to `app/services/llm/providers/` and the factory

### Requirement: Structured outputs are validated

The `LLMProvider.generate_structured()` method SHALL return an instance of the requested Pydantic model, or raise `LLMInvalidResponse`. It SHALL NEVER return a malformed object that fails validation downstream.

#### Scenario: Diagram generation produces a valid Diagram

- **WHEN** a caller invokes `provider.generate_structured(messages, schema=Diagram)`
- **THEN** the return value is an instance of `Diagram` that has already passed `Diagram.model_validate`
- **OR** an `LLMInvalidResponse` is raised with a clear diagnostic

#### Scenario: Adapter retries once on validation failure

- **WHEN** the underlying provider returns JSON that fails Pydantic validation
- **THEN** the adapter retries the request exactly once with a stricter system message
- **AND** if the retry also fails, `LLMInvalidResponse` is raised

### Requirement: Streaming returns prose as it is generated

The `LLMProvider.stream()` method SHALL be an async generator yielding `str` chunks. Streaming SHALL NOT be supported on `generate_structured` (structured outputs return only the final validated object).

#### Scenario: Stream yields incremental text

- **WHEN** a caller iterates `async for chunk in provider.stream(messages)`
- **THEN** each `chunk` is a non-empty string containing newly produced text
- **AND** the concatenation of all chunks equals the full response

#### Scenario: Stream is not available for structured outputs

- **WHEN** a caller tries to stream a structured generation
- **THEN** the protocol surface does not offer such a method
- **AND** the documented pattern is to call `generate_structured` and render its result whole

### Requirement: Embeddings via a separate protocol

The backend SHALL expose an `Embedder` protocol (separate from `LLMProvider`) for text-to-vector embedding. Callers obtain an instance via `get_embedder()`. The `EMBEDDER` setting (format `<provider>/<model>`) routes to a possibly different provider than chat.

#### Scenario: Local embeddings + cloud chat coexist

- **WHEN** `LLM_PROVIDER=anthropic` and `EMBEDDER=ollama/nomic-embed-text-v2-moe`
- **THEN** `get_llm()` returns an `AnthropicProvider`
- **AND** `get_embedder()` returns an `OllamaEmbedder` using the configured local model

#### Scenario: Anthropic does not advertise an embedder

- **WHEN** `EMBEDDER=anthropic/anything` is configured
- **THEN** `get_embedder()` raises `LLMConfigError` with a message explaining that Anthropic has no first-party embedding API at this time

### Requirement: Operational guardrails enforced in the provider layer

Every adapter SHALL reject messages whose total character length exceeds `MAX_INPUT_CHARS`. Every adapter SHALL clamp `max_tokens` on outbound calls to at most `MAX_OUTPUT_TOKENS`. These checks SHALL live in the shared base class, not in each adapter.

#### Scenario: Oversized input is rejected before the network call

- **WHEN** a caller passes messages whose combined content exceeds `MAX_INPUT_CHARS`
- **THEN** the adapter raises `LLMError` (subclass `LLMInputTooLarge`) before any network request is made
- **AND** no token is spent

#### Scenario: Output token cap is enforced

- **WHEN** a caller requests `max_tokens=10_000` and `MAX_OUTPUT_TOKENS=2048`
- **THEN** the value sent to the provider is `2048`

### Requirement: API keys never leak

API keys configured in `Settings` SHALL NEVER appear in log lines, exception messages, error responses, OpenAPI schemas, or any other output the backend produces.

#### Scenario: Provider error does not include credentials

- **WHEN** a provider call fails with a wrapped exception
- **THEN** the resulting `LLMError` message and traceback contain no fragment of any API key
- **AND** any log line emitted by the adapter contains no fragment of any API key

#### Scenario: Frontend never receives keys

- **WHEN** any HTTP response is generated by the backend
- **THEN** the response body and headers contain no API key

### Requirement: Provider selection is configuration-driven

The factory `get_llm()` SHALL return an instance whose concrete class is selected by `Settings.llm_provider`. Switching providers requires a configuration change only.

#### Scenario: Switching providers without code change

- **WHEN** `LLM_PROVIDER=anthropic` is set and the backend boots
- **THEN** `get_llm()` returns an `AnthropicProvider`
- **AND** no Python source has been modified

#### Scenario: Unknown provider name fails loudly

- **WHEN** `LLM_PROVIDER=mistral` is configured but no Mistral adapter exists
- **THEN** the backend either fails fast at startup or `get_llm()` raises `LLMConfigError` on first use, with a message listing the supported providers

### Requirement: Typed error surface

All errors raised by the LLM layer SHALL be subclasses of `LLMError`. Callers SHALL be able to discriminate failure modes via concrete subclasses (`LLMConfigError`, `LLMTimeoutError`, `LLMInvalidResponse`, `LLMRateLimited`, `LLMInputTooLarge`) without parsing message strings.

#### Scenario: Router handles rate limiting distinctly

- **WHEN** a future `POST /generate` router receives `LLMRateLimited`
- **THEN** it returns HTTP 429 with a `Retry-After` header
- **AND** it does not return 500
