## Context

Tangram is pre-alpha. We have a JSON schema for diagrams (`docs/schema/diagram-v0.md`), an ADR for guardrails (`ADR-0001`), and an ADR for adopting OpenSpec (`ADR-0002`). What we lack is a runnable system: no backend, no storage, no `pip install` path that ends in a working `/health`.

This change is the smallest set of artifacts that makes the project bootable end-to-end, without introducing user-facing behavior, and **without requiring Docker to develop locally**.

Constraints we honor:

- **Self-host first**: every contributor must be able to clone, run, and start contributing on their own machine.
- **Frictionless setup**: `pip install -e ".[dev]"` followed by `uvicorn app.main:app --reload` is the entire local-dev story. Anything more is friction we will pay for in lost contributors.
- **No premature features**: this proposal stops at `/health` plus storage scaffolding. LLM endpoints, patterns library content, persistence routes, and the editor are out of scope here.
- **SDD-aligned**: Pydantic schemas are the source of truth and are placed where future codegen can find them (`backend/app/schemas/`).

## Goals / Non-Goals

**Goals:**

- A FastAPI app that boots on `uvicorn` and responds on `GET /health`.
- A project layout that future contributors can extend without re-organizing (`core`, `middlewares`, `routers`, `schemas`, `tables`, `services`).
- Pydantic schemas matching `diagram-v0.md` available for import by future routers and services.
- A defined storage layout: diagrams as JSON files under `<DATA_DIR>/diagrams/`, Chroma vector store under `<CHROMA_PATH>`.
- A `.env.example` that documents every configurable surface.
- Zero required services for local development. Docker is optional, for production deployments.

**Non-Goals:**

- LLM providers, prompts, or anything that calls a model.
- The diagram-generation or analysis endpoints.
- Persisting or loading diagrams to disk (only the directory layout and config is established here — actual save/load endpoints come with `add-diagram-persistence-routes`).
- The patterns library content, embeddings pipeline, or seed script (those land in `add-patterns-library-and-rag`).
- Frontend, codegen pipeline, editor UI.
- Authentication or multi-user features.
- CI workflows (a follow-up proposal handles that, after the LLM provider abstraction lands).

## Decisions

### Backend layout: feature-folder per concern

Use `app/{core,middlewares,routers,schemas,tables,services}` rather than a flat `app/` or a domain-driven layout (e.g. `app/diagrams/{router,schema,service}`).

- **Why**: this is the most common shape across mid-sized FastAPI projects; new contributors recognize it instantly. The domain-driven layout is cleaner once the project has 3+ domains, but Tangram has effectively one domain (diagrams) for the foreseeable future.
- **Alternatives considered**: flat `app/` (rejected — gets unreadable past 5 files), domain-driven `app/diagrams/...` (rejected — premature for the size of the codebase).
- **`tables/` is intentionally empty in MVP.** No relational tables are introduced. The folder remains as a placeholder for Phase 2/3 if we ever migrate to a relational DB.

### `pyproject.toml` only — no `requirements.txt`

The project is declared as an installable package via `pyproject.toml` (PEP 621). Production deps live under `[project.dependencies]`, dev deps under `[project.optional-dependencies.dev]`. Tool config (ruff, pytest) lives in the same file under `[tool.*]`.

- **Why**: PEP 621 is the modern standard; one file replaces `setup.py`, `setup.cfg`, `requirements.txt`, `requirements-dev.txt`, `.flake8`, `pytest.ini`, `mypy.ini`. Compatible with `uv`, `poetry`, `hatch`, and plain `pip`.
- **Alternatives considered**: `requirements.txt` only (rejected — no metadata, no dev/prod split, no tool config).

### Pure Pydantic for `schemas/`, no SQLModel in MVP

The project's terminology is set by [memory and convention](../../../docs/architecture/0002-openspec-for-change-proposals.md) as well as in this proposal: `schemas/` for Pydantic data shapes, `tables/` for any future ORM models. With no relational DB in MVP, no SQLModel is needed; pure Pydantic suffices for validation and OpenAPI generation.

- **Why**: removes one dependency. `Diagram` is wire-shaped, not row-shaped, in MVP.
- **Alternatives considered**: keep SQLModel "just in case" (rejected — dead weight; we add it back if/when a real table appears).

### Filesystem storage for diagrams

Diagrams are stored as one JSON file per diagram, under `<DATA_DIR>/diagrams/<id>.json` where `<id>` is a ULID generated by the backend.

- **Why**: diagrams are documents, not records. The JSON-blob shape we already chose for the schema makes file-on-disk a perfect fit. Backups are `cp -r`. Contributors can inspect data with `cat`. No DB driver, no migrations, no ORM.
- **Alternatives considered**: SQLite single-table-with-JSONB (rejected — adds a dependency for no benefit at our scale), Postgres + JSONB (rejected — adds Docker), individual node/edge rows (rejected — schema churn would force migration on every change).

### Chroma for the patterns vector store

The patterns library (curated `.md` files in `patterns/`, landed in a future proposal) is embedded into a Chroma file-based store at `<CHROMA_PATH>` (default `data/patterns.chroma/`).

- **Why**: Chroma is mature (3+ years), file-based (no server), `pip install`-able, and is the de-facto integration in `langchain` / `llamaindex` for the kind of small curated corpora we will have. Bundleable in the repo (we pre-compute embeddings and ship them).
- **Alternatives considered**: pgvector (rejected — requires Docker for Postgres, contradicts the no-Docker dev story), sqlite-vec (rejected — too new, smaller community, less stable for an MVP), LanceDB (rejected — file-based and good but less common in Python LLM stacks; harder to onboard contributors), FAISS + pickle (rejected — minimal features, manual indexing).
- **Phase 2 escape hatch**: if we ever add multi-user / collaboration, we are likely already adding Postgres for diagrams, and migrating Chroma → pgvector is a straightforward re-embedding.

### Pydantic camelCase aliases on the wire

Schemas use Python `snake_case` internally (`created_at`, `data_flow`) but expose `camelCase` on the JSON wire (`createdAt`, `dataFlow`) via `Field(alias=...)`. The schema doc (`docs/schema/diagram-v0.md`) is the source of truth — wire format must match it. Models that have aliases set `model_config = ConfigDict(populate_by_name=True)` so Python callers can use either form.

- **Why**: idiomatic Python on one side, idiomatic JSON/TS on the other, with no manual translation layer.
- **Alternatives considered**: snake_case on the wire (rejected — TypeScript codegen would feel non-native), camelCase in Python (rejected — fights every linter).

## Risks / Trade-offs

- **Risk**: filesystem storage limits concurrent writers → **Mitigation**: MVP is single-user self-hosted; concurrent edits to the same diagram are not a real scenario yet. When collaboration arrives, we re-evaluate.
- **Risk**: Chroma's on-disk format may evolve and break backwards compatibility on upgrades → **Mitigation**: pin Chroma version in `pyproject.toml`; document `tangram seed` to rebuild the store if upgrade requires it.
- **Risk**: feature-folder layout will need refactor when we hit multiple domains → **Mitigation**: the codebase is small; we will refactor in a single PR when the second domain shows up.
- **Risk**: `.env.example` drifts from real config requirements → **Mitigation**: lint rule (future) verifying every `Settings` field has a matching entry in `.env.example`. For now, manual review per `CONTRIBUTING.md`.
- **Trade-off**: this proposal documents work that has been partially scaffolded already on the current feature branch. We accept the slight retroactivity for the sake of getting OpenSpec into the workflow with a real, useful first proposal rather than a contrived one.

## Migration Plan

This is the project's first runtime. There is nothing to migrate from. Rollback = revert the PR.

## Open Questions

- Do we want a `Makefile` or `scripts/` entry points (e.g. `scripts/dev.sh`) to wrap common commands, or is a documented README sufficient? Leaning toward "README only" until we feel real pain.
- Should we lock dependency versions in a `requirements.lock.txt` for reproducibility? Defer until CI exists — at that point we will pick `uv pip compile` or `pip-tools`.
- Health check shape: `{ status, name, version, environment }` is the current default. If a future load-balancer or k8s probe expects a different shape, we extend it then.
